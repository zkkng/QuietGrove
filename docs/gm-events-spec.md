# GM events, bot attendance, and monster incidents

Date: 2026-09-29. Audit and implementation specification only. No gameplay changes, deployment, live spawning, or capacity benchmark were performed.

## Outcome

One event framework must support a human GM host, a bot GM host, and a player command that requests an approved bot-hosted event. Every host uses the same event definitions, registration, announcements, attendance, rules, start/end transitions, rewards, and cleanup. Bot hosts receive narrow event-service capabilities; they do not receive an unrestricted GM account or execute arbitrary command strings.

The crowd objective is the largest **playable, measured** crowd the actual server and supported legacy client can sustain, including large numbers of active bot participants. Fifty is an old command default, not a capacity finding. Do not import the party-companion cap of 30 into this system. Measure progressively into hundreds and, if practical, thousands; identify the bottleneck and improve it before accepting a low ceiling. Visible spectators and active participants are separate reported counts. A sea of cheap spectators must never be presented as thousands of fully simulated competitors.

Summoning incidents may be announced or silent. Actual nearby population, awareness, travel, ability, resources, personality, and available groups determine the response. Reinforcements can grow with incident age but remain finite. A failed defense and a dangerous town that remains occupied are valid outcomes. No manufactured winning army, automatic boss weakening, or magical knowledge for distant bots.

### Existing lifecycle and command defects

`CommandsExecutor` registers player `joinevent`/`leaveevent`, GM3 `startevent`/`endevent`/`startmapevent`/`stopmapevent`. `summon` is an alias of **warphere**, not a monster command. Preserve that meaning.

- `StartEventCommand` installs one `Event(mapId, limit)` per channel and broadcasts world-wide. Default is 50; it parses params[0] only when params.length>1, so the normal single count argument is ignored. It can overwrite the current event. Cross-channel announcement versus channel-local lookup needs a join policy.
- `Event` is just mapId and a mutable remaining limit. `JoinEventCommand` separately checks/decrements limit, saves EVENT location, assigns team by remaining-limit parity, and warps. It is not atomic admission. NPC entry duplicates this logic, and some assistants only reject instead of joining.
- `EndEventCommand` closes entry by clearing the channel reference; it does not finish a game. `StopMapEventCommand` changes a boolean only; it does not cancel OX/Coconut/Snowball timers or undo per-character timers.
- `LeaveEventCommand` increments whichever event is currently on the channel, without event identity; the inspected path does not clear the saved location. Repeated leave or a replaced event can corrupt capacity. NPC leave paths also increment counters.
- `MapleMap.startEvent(chr)` starts Coconut/OX globally, Fitness/Ola only on that character, and Snowball only for one team. Replace the fragmented lifecycle behind compatibility commands, not by putting more host-specific branches around it.
- Winner NPC 9000002 grants item 4031019 and warps to saved EVENT location, relying on presence in the winner map. There is no audited event-result claim token. Validate eligibility, one-time grant, inventory-full retry, missing return location, and bots' economy treatment.
- `ChangeMapHandler` resets Fitness/Ola timers based on map ID before fully accepting the portal and without null guards. Finish must be an authoritative transition for a registered entrant reaching a valid finish portal.

## One framework and contracts

Use `GmEventService` with immutable `EventDefinition` registry and `EventSession` state. These are proposed names, not existing classes. Adapter interface: validate environment/config; prepare map; admit/remove actor; start; accept action; evaluate outcome; cancel; dispose. Human packet handlers and bot decisions call the same validated domain actions. No synthetic client packets and no separate bot scoring implementation.

Session fields: UUID/generation; definition/version; world/channel/map-instance identities; host identity/type; requester account; state; deadline; seeded randomness; configuration snapshot; roster/reservations/teams; return locations and prior activity IDs; owned monsters/reactors/drops/timers; reward ledger; capacity profile. IDs are preferable to long-lived Character references.

Lifecycle: DRAFT -> PREPARING -> REGISTRATION -> COUNTDOWN -> RUNNING -> SETTLING -> CLOSED. CANCELLED/FAILED converge on the same idempotent cleanup. Registrations arriving during a closed phase reject or wait according to definition; spectators are separate. One event can span multiple explicitly leased maps. Lease/map identity and generation prevent old timers mutating a restarted event. Initially serialize mutation per session/channel using an existing suitable executor or a narrow lock; never hold it across network sends/pathfinding.

Invariants:

1. A bot has one exclusive task lease. Event attendance cannot steal a merchant, dealer/host, tutorial/PQ actor, busy trader, recruited companion, or another event's bot. Initial eligible population is available supported social/training/wanderer bots. Restore their prior activity once on release.
2. Admission reserves capacity and bot atomically; active, pending, human, bot and spectator counts are explicit. Human admission reserve is configurable and included in capacity measurement. Team assignment uses actual roster balance, not mutable remaining-limit parity.
3. Every callback revalidates session generation, state, membership, world/channel/map identity, and actor life state. Cancellation invalidates pending arrivals, speech, actions, rewards, respawns and reports.
4. Dead/eliminated/spectating actors cannot affect competitive results. All humans and bots obey the same event geometry/action cadence/rules.
5. Result and reward are committed once. Reward identity is `(eventId, actorId, rewardKind)` with restart-safe claims if persistence is introduced. Packet retries and NPC repeat conversations cannot duplicate grants. For bots, default event prestige/internal inventory treatment must not create tradable market stock accidentally.
6. Cleanup releases only event-owned state. Restore portal/field restrictions/mute settings, timers, teams and temporary equipment; cancel bot tasks; clear saved EVENT location; return actors to valid saved map/portal or a documented safe fallback. Never kill all map mobs or remove unrelated player drops as event cleanup.
7. Human host logout pauses/transfers/cancels under explicit policy; bot host failure does the same. The host is presentation and authority context, not the sole keeper of event state. Restart recovery cancels/reconciles incomplete sessions without repeating rewards.

Use shared announcements with audience scope, join deadline, channel, location and eligibility. Bot speech uses a map-wide budget and varied staggering; no per-arrival chorus, coconut-score spam, repeated death spam, or LLM calls in high-frequency paths. Silent incidents bypass initial global announcements; their knowledge propagation is separate from theatrical chatter.

## Huge attendance: measure the actual playable ceiling

Existing scale mechanisms matter. `BotTickService` scans entries every 100ms and dispatches macro ticks to virtual threads, avoids overlapping ticks per bot, and stretches background cadence on sustained average dispatch lag above 1000ms (up to 4x). Its foreground exemption is not a license to mark every event bot unthrottled. `GCMovementDriver` runs observed movement at 50ms, heavy decisions at 100ms, unobserved movement at 250ms and idle at 1000ms. A crowd made visible to one human can promote many bots at once. Current thresholds protect background work but do not establish acceptable interactive event latency.

`EnvironmentManager` configures large training cohorts (e.g. 225 each for several Victoria towns, plus other areas); that is world population, not evidence that the same count works on one screen. Snapshot actual registry after startup: successful live bots by map/channel, level/job, resources, role and availability. Do not equate configured spawn count, registered bot count, moving bot count and rendered crowd.

Maintain three modes with explicit counts:

- **Participant:** authoritative event movement/actions/combat/resources/score. Retains fair action cadence; expensive planning can be cached/shared without changing result semantics.
- **Visible spectator:** real visible presence with sparse movement/emotes, no event score/damage/rewards. Still costs spawn packets, character/equipment rendering, memory and network. Town spectators remain vulnerable to an invasion unless placed in a genuinely safe area; calling a victim a spectator cannot grant silent invulnerability.
- **Off-screen attendee/traveler:** coarse intent/route progress where legally supported. Promote before entering observation or interaction range, with a bounded per-tick promotion queue. Never skip lethal map hazards or teleport through locked transit. Do not represent these as visible crowd.

Optimize from profiles: map-local spatial indexes, bounded candidate queries, cached/shared nav graphs and route segments, staggered planning and arrivals, common event clock, sparse speech, dirty-state updates, packet coalescing where protocol semantics allow. Avoid all-bots x all-mobs scans every 50ms and one scheduler per announcement. Active actors must retain responsive physics/action validation. Do not shed load by making only bots' hazards/damage disappear or changing competitive scores.

Legacy client constraints are independent of server CPU. Measure character spawn/equipment packets, movement/attack/buff fan-out, many unique avatar assets, pets/chairs/name tags, boss multipart effects, drops and damage numbers. One viewing human sees potentially O(B) traffic; H simultaneous viewers can create O(B*H) sends, plus any bot-recipient work in map broadcast paths. Verify whether dummy clients are skipped rather than assuming it. A headless server test cannot establish renderer/frame-time capacity. Custom-client optimizations may raise a separate capacity profile; baseline v83 must be tested and reported separately.

### Reproducible load matrix

Record commit, configuration, bot build profile, map/adapter, server CPU/RAM/JVM/GC, client build/hash/OS/CPU/GPU/resolution, client-network path, actual human viewers and simulated modes. First instrument and benchmark an empty map and normal world population. Candidate steps: 25, 50, 100, 200, 400, 800, 1200, 1600, then +25% while all gates pass. These are test steps, not a promise or imposed maximum. Start above a previously proven baseline when available. Record a failed step; bisect/refine around it, optimize, repeat. Test both all-active and realistic participant/spectator mixes.

For each step: staggered admission, synchronized start, normal steady play for at least ten minutes/full round, peak effects, human join/leave/map entry, mass elimination/result transition and cleanup. Run 1, 3 and 10 viewing-client cases where test machines permit; distinguish real render clients from network-only clients. Final candidate: three repeat passes plus 60-minute soak, multiple event cycles, normal background world load. Test OX motion spike, Fitness multi-map traversal, Coconut simultaneous hits, Snowball sustained melee, and invasion with real boss effects. One map's winner does not become a global cap.

Proposed playability gates, adjustable only by recording the new target before comparisons:

| Layer | Required measurements and initial pass target |
| --- | --- |
| Server responsiveness | Event action enqueue-to-apply p95 <=100ms, p99 <=200ms; clock drift <=250ms; measure macro and 50ms movement-driver scheduling lag separately. No continuously growing work queue. |
| Server resources | CPU/core saturation, allocation rate, heap after GC, GC p99 pause and maximum pause, thread/virtual-thread backlog, lock contention, DB time. | Gameplay | Accurate results, legal collisions/portals/targets, no ghost/double actors, responsive human inputs, readable rules/target selection, no chat flood; timers/rewards/cleanup correct at maximum load. Numeric FPS alone does not pass a visually unusable event. |

Publish `event-capacity-results` with highest passing active count, highest passing visible total, spectator mix, viewer count and first failing bottleneck per client/map/profile. Runtime admission limit is the minimum of tested server, tested supported-client, event/map, world availability and configured operator ceilings, with explicit configurable headroom (initial 15%). Push scale by optimizing and retesting; do not replace the unknown ceiling with a guess.

Runtime governor: monitor queue lag, outbound backlog and resources; close further admissions first, slow new arrivals, reduce optional spectator emotes/motion and unobserved planning, then offer overflow spectators/wait queue outside the crowded map. Restore slowly with hysteresis. Preserve active competition semantics. A sustained hard threshold can pause/cancel through normal cleanup with one clear announcement. Never silently despawn competitors or award fabricated results. Config includes active/visible/pending/world limits, human reserve, burst rate, promotion budget, headroom and measured-profile ID; unresolved/unmeasured profiles stay development-only until validated.

## Announced and silent monster incidents

### Human playtest requirements added 2026-09-30

- NPC GM events must never exceed **3 living boss encounters** or **30 living ordinary event mobs** at any given time. Include event-owned WZ summons and revives in the respective limits. Multipart pieces share one encounter identity. These limits are not an approved bot crowd capacity.
- Monsters and bot responders arrive in a slow trickle. Hosted boss additions are at least 15 seconds apart; ordinary mobs and responder departures are at least 2 seconds apart. Further waves wait for genuine victory and a 30-second intermission.
- Existing bots must actually attack through shared combat, take genuine HP/MP damage, and be able to die and recover. Real ability, supplies, willingness and travel remain required; do not manufacture a winning population.
- The host is an existing bot with full Wizet GM presentation and a visible `[GM]` name prefix. World announcement names the host and event location. Temporary presentation cannot alter canonical gear/stats or account privileges.
- The earlier unmanaged 100-monster Henesys test failed the human playtest and was cleaned by exact ownership. It is not a supported launch path or release evidence.

`IncidentService` may be an event adapter sharing leases, host permissions, ownership and cleanup, while allowing public-world participation without registration. Incident record: encounter/template and owned object IDs; origin map/position/time; announcement mode; threat/evidence; current phase; witness/report graph; finite eligible candidate snapshot/index; arrivals/deaths/retreats; expiry/operator policy. Normal field bosses and summoned events must not accidentally share identity because they use the same monster template.

Awareness:

1. A bot on the affected map can notice a monster through local perception or experience actual attack/death. Witnesses may flee, warn nearby bots, report to a group or town, or seek help. Perception and report delays vary, with source, timestamp and location confidence.
2. Announced incidents seed only the defined announcement audience immediately. Silent incidents have no global omniscient seed. A bot entering through a normal route can independently discover one.
3. Reports spread across existing social/group contacts and locations with bounded fan-out and deduplication/TTL. Internally distribute awareness without emitting one chat line per graph edge. Shared world event bus gains explicit typed incident signals; current `EventType` only covers reward/level/scroll/chat/emote/map-entry signals, not invasion lifecycle.
4. A candidate must be available, aware, able to reach the map, and willing. Decide flee/hide/watch/report/prepare/gather-party/travel/fight/support based on level/job/build, observed hit/survival odds, finite potions, route cost, group roles and personality. Knowledge does not imply immediate combat or immediate arrival.

Arrival pressure increases with incident age as reports reach more eligible population and groups prepare, but availability is a finite set. Model each bot's awarenessTime + decision/preparation delay + real route ETA, then release arrivals in bounded staggered batches; revalidate on departure and arrival. Group readiness may delay an otherwise strong member. Do not spawn a fixed additional wave every minute forever. Once all informed suitable reachable volunteers are committed, dead, recovering, busy or unwilling, recruitment plateaus. Remote travel/boats and channel boundaries are real costs; no GCTravel no-route fallback teleport into an incident.

Locality examples to validate:

- **Zakum in Leafre versus Perion:** same threat, different actual population/routes. The audited environment setup has Perion training cohort 225 level 10..65, 20 beginners, and ambient Perion level 10..65; TownPresence.yaml has no Leafre entry and the inspected training initialization has no Leafre cohort. Therefore stronger Leafre defense is a desired future population property, not current evidence. First inventory running bot distribution. If high-level Leafre residents are wanted, add them as an explicit world-population change with coherent builds and budget; never materialize them on summon. With no eligible residents the initial response may be almost empty.
- **Silent Crimson Balrogs in Henesys:** nearby low-levels encounter real lethal danger, some die/flee and leave the area quiet. Early reports are local; stronger reachable volunteers trickle in later if they exist. Population depletion, death/retry cooldowns and fear can let Balrogs remain for a long time. A successful clear is possible, not guaranteed. Resolve template via registry: local String.wz contains several different Crimson Balrog names/IDs; 8150000 is one candidate, not permission to interchange event/quest variants.
- **Announced weak invasion:** many willing nearby actors may overwhelm monsters quickly. Attendance may be enormous within measured limits, while reinforcements still need travel and live actors. Stops naturally on actual defeat.

Deaths stop all attacks, buffs, scoring and participation immediately. Use canonical dead state and appropriate visible tombstone/animation with bounded dwell, legitimate town revival and finite recovery/resource cost. A casualty may remain as a dead actor briefly; long-term danger persists through absent/retreated people and hostile mobs, not unbounded permanent corpse objects. Initial configurable retry policy: at least 60 seconds plus travel and preparation, increasing after repeated deaths; retreat before repeated hopeless fights. Some personalities risk an initial mistake; evidence updates subsequent decisions. Return to previous safe activity when resolved, abandoned or released; never resume an invalid old combat callback.

### Combat and encounter prerequisites

Combat credibility blocks invasion release. The companion spec finds `BotContactDamage` explicitly cosmetic (hurt packet/knockback, no HP loss/death), generic outgoing `BotDamageModel` bands rather than accuracy/defense, incomplete real skill/MP/potion checks, and cosmetic bot self/ally buffs. Reuse the companion combat implementation as it lands. Event participants need the same actual hit/miss, defense, elemental rules, HP/MP, consumables, learned skill, healing, status, buff strength and death contract. A high-level label alone is not boss capability. Training accuracy misses differ from cooldown/out-of-range failures.

Additional blocker: `Monster.getNextControllerCandidate` excludes bots. Human clients ordinarily control monster movement/actions, so a bot-only or unobserved incident cannot assume the boss will move or cast. Audit current monster control/fallback architecture and provide a bounded authoritative server-side incident controller or a verified equivalent. It must use real WZ action/skill timing, targets and defenses, avoid duplicate human-controller damage, and transfer control without freezing/resetting the encounter when a human arrives/leaves. Tests with zero humans and only a hidden GM are mandatory. Cosmetic incoming contact alone does not cover projectiles, area skills, statuses, dispels, summons or map hazards.

Encounter registry distinguishes `SINGLE_MOB` from multipart/phase definitions. Verify template, linked WZ, HP/attack/avoid/immunity, bounds, footholds, spawn position, phases/parts, summons/revives, drop/EXP/quest credit and finish rule.

- Zakum IDs verified in `MobId`: body 8800000, arms 8800003..8800010. `ZakumCommand` spawns fake body plus arms. `MapleMap.killMonster` scans all arms in the **map** and activates the first body after none remain; this is not encounter-scoped and can interfere with multiple Zakums. Require one encounter per map until fixed, or partition by encounter ID. Body phase/revive ownership must propagate, and final victory is final required phase death, not one arm/template disappearance.
- Horntail helper creates intro/root/parts and listeners forwarding part damage; `Monster.killBy` follows WZ revives and parent relationships. Preserve authoritative damage attribution across parts, prevent double EXP/drops and cleanup descendants. Verify full phase completion rather than treating a root HP bar as the encounter.
- Town geometry is not a boss arena. Validate boss bounds, correct ground placement for parts, reachability for melee/ranged/support, climb/portal/respawn locations, attack rectangles and movement limits. A visually present boss on a roof or buried body may be unplayable. Reject incompatible encounter/map placements with reasons or require a reviewed placement profile; do not fake full encounters with one decorative body.
- Spawned mobs are finite by default; normal map respawn must not recreate incident mobs. WZ summons/revives belong to the incident and consume a separate spawn budget. Monster defeat and administrative removal differ: cleanup must not fire legitimate kill rewards/quests/next phases. Audit `killMonster` null-killer early path versus `killBy`/revive callbacks and event script listeners.
- Maintain actual contribution and normal kill/drop ownership, then event-specific rewards separately. Support attribution shares companion ledger contracts; spectators, parked bots and mere last frame presence do not get fabricated credit. Choose explicit PvE death EXP/drop policy for public town incidents and apply consistently to humans and bots. Bots cannot loot-lock or flood economy through event reward automation.

## Acceptance and regression gates

- Run the same definition through human host, bot host and player request. Same roster/rules/results/rewards; only introduction/control differs. Unauthorized requester cannot choose spawn/reward/map overrides. Duplicate requests coalesce and cooldowns are account-scoped.
- Race 100 joins for the final seats and race a companion invite/event reservation for one bot. No oversubscription, duplicate owner, team imbalance from failed joins, or lost prior activity. Test channel mismatch and full map entry during admission.
- Cancel/restart while registration, countdown, question, delayed cast, corpse dwell, respawn, arrival and reward delivery are pending. Old generation has zero effect. Host logout, bot host despawn, map reload and server shutdown cleanly reconcile. Repeat leave does not add seats or grant rewards.
- OX: exact selected round count, valid question keys and left/right mapping, neutral/ladder elimination, no prizes for GM/spectator exemption, mixed bot correctness; insufficient population does not crash. Course events: all entrants get same remaining deadline, correct/wrong portals and speed limits, real falls/death, no-route travel cannot win, valid finish only once. Missing scripts prevent approval.
- Coconut: null/out-of-range/stale IDs reject safely; invalid team/member/distance/skill/attack cadence cannot score; simultaneous last hits score once; ties and overtime end once; no mass score-chat flood. Snowball: both teams start/stop, snowman damage/recovery affects intended team, correct winner/draw/time/distance handling and packet content, no attacks after end.
- Reward inventory-full retry is safe; reconnect/duplicate NPC calls cannot duplicate claims; missing saved return gets safe fallback; cleanup preserves unrelated mobs/drops/portal state. Run two cycles without restart and compare timer/registry/heap baselines.
- Capacity report includes real client frame time and server/network latency at peak effects, many unique avatars, spawn bursts and 1/3/10 viewers where available. Pass final soak at chosen profile with headroom and correct results. Report maximum active versus visible separately. No measured result exists yet.
- Silent incident: an isolated distant bot has no awareness before a valid report/visit; nearby witnesses react first, reports spread with delay, unavailable companions/merchants stay owned. After deaths, retries respect cooldown and routes; no endless spawn-to-win reinforcements. With no suitable population, threat persists until policy/operator resolution.
- Zero-human boss test: boss moves/casts and bots take real HP/status damage; human arrival/control transfer neither duplicates nor stops damage. Confirm low accuracy against strong bosses, finite potions, real Heal/HS/support, retreat, death and no immortal spectators inside danger.
- Full Zakum: all arms, body activation and every phase, boss attacks at curated town geometry, final death attribution; cancel at each phase removes only owned descendants without drops or revival. Test second same-template encounter interference explicitly. Horntail receives equivalent multipart tests before approval.
- Compare same seeded incident at Perion and Leafre using actual runtime population and route distribution; record awareness-to-arrival histogram, participant levels/jobs, deaths, retreat and plateau. Stronger Leafre response is accepted only when a real stronger population exists. Silent Henesys Balrogs may leave many casualties and remain undefeated.
